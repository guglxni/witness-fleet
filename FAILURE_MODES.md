# Witness Fleet Failure Modes and Recovery Specification (Proposed)

**Status:** failure handling and recovery contract only; not implemented or exercised. Every status, threshold, and recovery behavior below is proposed. No live run, database fault injection, model inference, or simulator run occurred.

## 1. Operating rule

Witness Fleet is simulation-first. One MuJoCo physics owner controls world stepping; robots act through bounded adapters. The deterministic planar adapter is for unit tests only. At every state transition, distinguish: (a) what is physically true in evaluator-only simulator truth, (b) what the sensor observed, (c) what the graph/policy currently permits, (d) what the model proposed, and (e) what command/verification actually returned.

On uncertainty that affects policy, safety, evidence freshness, task ownership, or side-effect status, stop or hold the affected task, preserve state, explain the uncertainty, and reconcile before resuming. A recovered process must recompute permissions from current graph and evidence; it must not resume a cached plan just because a workflow checkpoint says “next.” Local emergency stop behavior is outside database/model availability, but this simulation design is not certified functional safety.

`UNKNOWN` is a first-class result. It is not equivalent to `false`, `failed`, `not found`, `empty`, or `safe to retry`. The system makes no exactly-once distributed side-effect promise.

Hold/stop affected robots using local adapter behavior; do not convert failure to empty restrictions or allow. No hidden in-memory authority cache. | `EV-008`; simulate graph outage at read, claim, policy recheck, and post-action write. Assert no new dispatch and honest status. |

Never convert persistence errors to empty success or `trace_persisted=true`. | `EV-011`, `EV-014`; fail writer at each event boundary. |

## 3. Recovery-state semantics (proposed)

### 3.1 Command state machine

```text
PREPARED → SENT → ACCEPTED → RUNNING → CONTROLLER_DONE → OUTCOME_VERIFIED
             ↘ UNKNOWN (reconcile; preserve last known state)
FAILED / CANCELLED retain partial effects and require inspection where relevant
```

`PREPARED` means intent and idempotency key are durably recorded before send. `SENT` indicates transport attempt, not receipt. `ACCEPTED`/`CONTROLLER_DONE` are adapter responses, not verified physical completion. `OUTCOME_VERIFIED` requires fresh sensor evidence that satisfies all declared postconditions and current policy/task dependencies. `UNKNOWN` requires reconciliation; it cannot transition directly to a second physical execution. Terminal failure may permit a new command only after fresh state, a new decision, and a new command ID or explicitly idempotent replay contract.

### 3.2 Task/claim state machine

Claim transitions use expected task version and policy epoch. A successful CAS creates a fencing token and lease. Lease expiry moves to `REASSESS`, not `READY_TO_REPEAT`. New claimant reads latest graph and command ledger, reconciles outstanding action, validates evidence freshness and policy, then creates a new claim/token. The adapter rejects all older tokens. A task completes only after postconditions are verified, not because the controller returned success or a prior workflow checkpoint says complete.

### 3.3 Recovery across durability boundaries

Treat these as four different events: (1) coordinator process restart with DB untouched; (2) FalkorDB process restart with configured data directory; (3) container recreation with configured persistent volume; (4) backup restore into a clean instance. Test each independently. After any recovery, wait for schema constraints/indexes to be operational, verify expected graph/policy versions, read back exact stable IDs, reconstruct pending work, and reconcile all `SENT`/`UNKNOWN` commands with the adapter before dispatch. If recovery cannot distinguish committed from uncommitted side effect, maintain hold and escalate.

## 4. Operator-facing failure reporting

Every status should expose, without leaking other tenants' data:

- affected task/robot and last safe checkpoint;
- failure class and whether it is `denied`, `stale`, `unavailable`, `invalid`, `unknown`, `needs_approval`, or `verified_failure`;
- graph/policy/task version and relevant evidence IDs/source revision IDs;
- command ID/idempotency key and current reconciliation status, when applicable;
- safe available next step: inspect, wait/reconcile, request approval, restore, or manual escalation;
- whether action was attempted, dispatched, acknowledged, observed, verified, or left unknown.

Do not show “success” for a command acceptance, generated answer, or source retrieval alone. Preserve raw attempt/outcome records even when an operator resolves the incident manually.
