# Witness Fleet — proposal

**Proposal, not a completed implementation.** Working title; three intended tracks: Agents That Act on Connected Data, Agent Memory and Coordination, Company Brain.

## Short pitch

A scout clears the view. A recovery robot clears the floor. The courier still refuses to move—and shows the exact current company decision that forbids it. Witness Fleet is a simulated robot team whose actions depend on fresh physical evidence, persistent shared memory and source-backed operational authority stored in FalkorDB.

## Why this is one product

Physical incidents, task dependencies and company restrictions describe the same operational decision. A graph connects the obstructed corridor to affected work, capable responders, evidence, owners and release conditions. Persistent claims and command receipts prevent a restarted coordinator from repeating uncertain actions. A narrow System One assessor can prioritize ambiguous evidence, but deterministic checks remain responsible for permission.

The graph must change the action, not simply explain a decision made elsewhere. Updating a real synthetic source/release changes the canonical witness and the courier's behavior while geometry stays fixed; changing physical clearance can block movement even with policy permission.

## Technical contribution to demonstrate

An auditable recovery contract joining:
- observation versus hypothesis versus predicted effect;
- robot/payload-conditioned pre/post verification;
- dependency/capability/resource assignment;
- current source/revision/span/owner/policy proof;
- fenced claims, explicit unknown effects and restart reconciliation;
- optional bounded semantic assessment with measured risk/coverage/cost.

This is an engineering synthesis, not a claim to invent graph robotics, active perception, centralized task allocation or agent memory. KGLAMP, VAP-TAMP and HUME are close prior work.[86][100][101] LiP-LLM, RobotFleet and SayComply further narrow any originality claim; the package explicitly records what is borrowed and what is new application glue.[105][148][116]

## Why System One can help—and when it should be removed

The best first use is an atomic support/contradiction judgment over exact retrieved spans, preserving contradictory evidence and complete deterministic policy enumeration. A later use selects among already eligible investigation branches. Jev-specific benchmarking motivates per-family calibration; JevOut motivates plausible-context invariance tests; REFLEX motivates comparing the selective cascade against a cheap generator cascade rather than assuming a win.[84][85][156]

If matched held-out evaluation shows no useful ranking/cost benefit, leave it disabled and publish the result. The product should still work as a rigorous graph-driven baseline. This is stronger than attaching a model badge to every action.

## Delivery

A local reproducible simulation, operator dashboard, canonical schema/query files, synthetic source corpus, raw episode traces, negative/failure tests, restart/restore evidence, model comparison if actually run, clear third-party notices and AI-assistant disclosure. Public publishing/submission occurs only after user approval. No real hardware or private enterprise documents required.

## Honest scope

No application implementation or live benchmark has been performed by this specification task. No provider performance figures are our results. The server's SSPL license and proprietary hosted models mean the whole stack is not OSI-approved FOSS. The original code/assets and participant contribution must be identifiable and understood.[30][39]
