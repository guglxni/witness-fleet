# Canonical graph schema and query contracts

**Proposed schema. No Cypher in this file has been runtime-tested.** Implement and contract-test on the pinned FalkorDB build before claiming compatibility. Use stable business IDs, not internal recycled node IDs. This file owns relationship direction; diagrams and queries must match it.

## 1. Graph and identifier conventions

`wf:<tenant>:ops` owns operational state. `wf:<tenant>:corpus` and explicitly discovered SDK companion keys own retrieval. Tenant input is resolved from trusted server context, never an arbitrary user-selected graph name. Every node also has `tenant_id` for defense in depth. IDs are opaque strings generated by the application with explicit type prefixes; never infer identity from display name.

Common envelope: `id`, `tenant_id`, `schema_version`, `created_at`, `recorded_at`. Events additionally carry `event_id`, `occurred_at`, `world_tick`, `producer_id`, `payload_hash`. Integers are nonnegative within documented limits; hashes identify bytes/normalized text, not human truth or authorization.

A connected **branching subgraph** provides the Company Brain proof. There is no fictional linear `Source → Revision → Owner → Decision → Restriction` chain. Stored direction and query matching are authoritative here.

## 4. Proposed read templates

These examples illustrate contract shape, not a guaranteed valid migration/query. Client parameters must use the pinned client's parameter interface; never interpolate strings.

### Q-001: restriction evidence for a corridor

```cypher
MATCH (d:Decision)-[:IMPOSES]->(r:Restriction)-[:APPLIES_TO]->(c:Corridor),
      (d)-[:OWNED_BY]->(o:Owner),
      (d)-[:SUPPORTED_BY]->(s:EvidenceSpan)-[:IN_REVISION]->(v:Revision)-[:REVISION_OF]->(src:Source)
WHERE c.id = $corridor_id AND c.tenant_id = $tenant_id
RETURN d, r, c, o, s, v, src
```

Do not `LIMIT top_k` over governing restrictions. This returns candidate governance paths; deterministic code validates approval/effective interval/scope and all matching releases/permissions with Q-002. A missing required evidence edge makes a governance record incomplete, **not invisible permission**: a separate integrity query must detect restrictions lacking complete support, and authorization fails closed on them.

### Q-002: release/permission and governance completeness

Run a tenant-wide governance-integrity scan before corridor authorization. Start independently from **every staged/promoted governance entity** (`Decision`, `Restriction`, `Permission`, `Release`, `ApprovalEvent`, `Owner`) rather than only traversing well-formed restrictions. Validate required cardinality and direction of `IMPOSES`/`GRANTS`/`LIFTS`, owner/approval, source support and scope/target edges. A Decision whose `IMPOSES` edge is absent is also an integrity failure, even when its Restriction has become unreachable. Pending/unapproved proposals remain inert and distinct from corrupted previously active records. Missing/ambiguous scope or absent `APPLIES_TO` targets must fail closed rather than fall outside the corridor query. Deny affected admissions, or all tenant admissions if affected scope cannot be determined, until explicit repair. Read all restrictions attached to the corridor, including incompletely connected ones; left-optional traverse their release and approval paths. Read all base permissions for the action. Output completeness flags and all current candidates; no model rank filter. Authorizer denies an active unlifted restriction, requests evidence/approval on inconsistent records and allows only with valid base permission plus all physical/task/resource guards.

### Q-003: affected tasks

Traverse `(Task)-[:USES]->(Corridor)` and reverse dependency links to downstream tasks. Bound traversal by validated acyclic task DAG and configured maximum depth. Return dependency witnesses and task versions. Detect truncation; never treat a partial frontier as complete.

### Q-004: ready frontier and eligibility

Return nonterminal tasks with all prerequisite tasks outcome-verified, required facts current and available capabilities/resources. The solver receives eligible pairs and explicit rejection reasons. It does not infer missing edges as capability.

### Q-005: verified episode candidates

Start from corridor/map/hazard/capability relations, retrieve verified episodes and procedure compatibility records, then re-ground under current policy/physical evidence. Similarity may order candidates; it cannot satisfy live preconditions.

## 5. Write transition contracts

- **W-001 append event:** stable event ID + payload hash. Same ID/same bytes is idempotent; same ID/different bytes rejects. Preserve event/ingestion time.
- **W-002 accept/refute fact:** validate observation support/freshness/scope, update derived fact version, invalidate dependent permissions, retain history.
- **W-003 claim:** expected task/resource versions + policy epoch + lease state; one conditional mutation returns winner/fence or conflict. Test exact query and all constraints under concurrency.
- **W-004 command intent:** bind stable command ID/payload hash to current claim and immutable AuthorizationReceipt before send. In the same tested conditional mutation increment `FleetState.dispatch_sequence` and append matching DispatchEvent, per RUNTIME.md. Validate receipt payload/actor/task/claim/resource versions, policy epoch, dependencies, integrity scan version and tick expiry; an old ALLOW receipt cannot admit changed state. No mutation can convert UNKNOWN to completed without evidence.
- **W-005 approve/release:** authenticated synthetic owner, explicit authority scope, expected epoch, named restriction, checked evidence; increment policy epoch and record actor/event plus sequenced DispatchEvent atomically under tested semantics. Validate explicit simulation-tick effective interval and tenant-wide governance integrity before promotion. No independent governance writer may skip the sequencer.
- **W-008 delivery acknowledgment/barrier:** idempotently retain event ID/hash/sequence, simulator applied tick and last-contiguous cursor; same identity/different hash rejects. Restart increments epoch and appends a barrier; gaps and unknown old command effects hold until RUNTIME reconciliation. Never skip a lost event.
- **W-006 complete task:** requires observed postconditions and receipts, not just successful API return.
- **W-007 source promotion:** immutable revision/span first, staged extraction second, approved typed governance third; record replay-safe projection receipt. No cross-graph commit assumption.

Database uniqueness/range indexes, mandatory constraints and their operational state need pinned runtime probes. A constraint request still pending is not protection. No SQL-style rollback claim for `MULTI/EXEC`.[10][31]

## 6. Conflict, temporal and migration rules

Overlapping valid restrictions accumulate. A release only lifts its named restriction for its explicit narrower/equal scope; it cannot erase others. Contradictory owner/approval records produce `NEEDS_APPROVAL`. Ingested_at never overrides effective interval; unsigned/newer text remains a proposal.

Schema migrations are versioned, idempotent where feasible, backed up and tested on disposable graph keys first. Operations and SDK migrations never share ownership. Validate no orphaned governance or cross-tenant edges, no DAG cycles, no stale active claim and exact source-span integrity before admitting traffic.
